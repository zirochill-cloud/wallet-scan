# Design-phase tooling. Not the application's runtime dependencies.
#
# NOTE: system pip cannot write to the shared interpreter prefix in this
# environment, and `--user` is disabled inside the venv. Use a project-local
# virtualenv, which is already gitignored:
#
#   python3 -m venv .venv
#   ./.venv/bin/pip install -r requirements-dev.txt
#   ./.venv/bin/python tests/test_phase0.py
#
# ---------------------------------------------------------------------------
# ONE COMMAND — the two DB suites (test_schema_smoke, test_ledger_live)
#
#   bash bootstrap_db.sh
#
# Stages the portable PostgreSQL binaries and the virtualenv under a SHORT
# path (%LOCALAPPDATA%\Temp\solscope-dbtest, ~60 chars), initialises a
# cluster, starts it on 127.0.0.1:5433, runs `solscope migrate` against its
# own scratch database, runs both DB suites, asserts the admin database still
# has 0 public tables, and stops the server again. Exit 0 only if everything
# passed — and a suite that SKIPs does NOT count: the script greps for each
# suite's final PASS marker, because both suites exit 0 when psycopg is
# missing. Repeatable: re-running reuses the venv, the binaries and the
# cluster.
#
# Why a script and not docker: Docker is not installed on this machine
# (checked 2026-10-26), and pgserver publishes no Windows build, so a native
# Windows PostgreSQL run locally is the only path that works here.
# ---------------------------------------------------------------------------

# Schema verification (tests/test_schema_smoke.py)
psycopg[binary]>=3.1      # direct PostgreSQL adapter
pgserver>=0.1.4; sys_platform != "win32"   # bundles a local PostgreSQL for tests without a daemon/docker (Linux/macOS only — on Windows the bootstrap_db.sh path below covers this)
#
# ---------------------------------------------------------------------------
# RESOLVED (2026-10-26): how the two DB suites run on Windows.
#
# The manual sequence below is now AUTOMATED by `bash bootstrap_db.sh` — run
# that instead. The steps stay here so the automation is auditable, and the
# short-path rule behind them is why the script exists at all.
#
# Chosen path: a NATIVE Windows PostgreSQL run locally, no admin rights needed,
# using EDB's portable server binaries. pgserver has no Windows build, so it
# cannot be the path here.
#
#   1. Download the portable binaries (no installer, nothing touches the system):
#        https://get.enterprisedb.com/postgresql/postgresql-16.6-1-windows-x64-binaries.zip
#      Extract only bin/ share/ lib/ (skip pgAdmin 4/ — its deep tree blows past
#      MAX_PATH and extraction fails with WinError 206).
#
#   2. Create the venv at a SHORT path. Under this project's very long path,
#      psycopg-binary fails to unpack its DLL:
#        python -m venv /tmp/pvenv       # = %LOCALAPPDATA%\Temp\pvenv
#        /tmp/pvenv/Scripts/pip install "psycopg[binary]" pyyaml
#
#   3. Init and start the server (again, short paths):
#        pgsql/bin/initdb.exe -D /tmp/pgdata-solscope -U postgres -A trust -E UTF8 --locale=C
#        pgsql/bin/pg_ctl.exe  -D /tmp/pgdata-solscope -o "-p 5433 -k /tmp -h 127.0.0.1" -l /tmp/pglog.txt start
#
#   4. Point the tests at it and run them with that venv's python:
#        export SOLSCOPE_TEST_PGDSN="host=127.0.0.1 port=5433 user=postgres dbname=postgres"
#        /tmp/pvenv/Scripts/python tests/test_schema_smoke.py
#        /tmp/pvenv/Scripts/python tests/test_ledger_live.py
#
# Verified 2026-10-26: both suites pass for real (41 tables in the scratch DB,
# migration runner tracked as a 42nd). Both suites create their OWN scratch
# database and leave `postgres` at 0 tables — assert that after any harness edit,
# because the conninfo-shaped DSN previously sent both suites straight into
# `postgres` instead of their scratch database, which passed vacuously.
# ---------------------------------------------------------------------------
#
# Windows note (verified 2026-10-25): pgserver publishes no Windows build, so
# test_schema_smoke.py and test_ledger_live.py cannot provision a database on
# Windows and exit 0 with "SKIP". Exit 0 is NOT a pass — point them at a real
# server with SOLSCOPE_TEST_PGDSN, or run them under Linux/macOS. psycopg's
# binary wheel also fails to unpack when the project path is near MAX_PATH
# ("No such file or directory ... psycopg_binary.libs"), so keep the checkout
# short or enable Windows long-path support.
